# ADR 0002: Pagination for every list endpoint

- Status: Proposed (needs director approval)
- Date: 2026-10-17
- Related: docs/spec.md sections "API outline" and "Engineering standards"

## Decision in one line

Every list in the API is returned one page at a time using a **bookmark** ("cursor") that remembers
the last item you saw, not a page number. Pages hold at most **100 items** (default **50**). The order
is always fixed and ties are broken by the item's unique id, so you never see an item twice or miss one,
even while new data is arriving.

Plain-English terms:
- **Offset pagination**: "skip the first 200, give me 50". Simple, but slow on big tables and it skips
  or repeats items when rows are added while you page.
- **Keyset (cursor) pagination**: "give me 50 items that come after this exact item". Fast and stable.
- **Tiebreaker**: when two items have the same sort value (for example the same timestamp), we also sort
  by their unique id so the order is always the same.

## Context

- CLAUDE.md: "cursor/keyset only, stable sort with unique tiebreaker, max page size."
- Lists include sites, rooms, racks, reservations, telemetry rollups, forecast runs, documents and
  planner questions. Telemetry tables can hold hundreds of millions of rows.
- Read target: **p95 <= 200 ms at 50 requests/second**. Offset scans get slower the deeper you go;
  keyset queries stay constant-time with the right index.
- Ids are UUIDv7 (time-ordered unique ids generated by the application), which makes a good tiebreaker.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| Offset/limit (`?page=5`) | Simplest; "jump to page 9" | Banned by CLAUDE.md; deep pages are slow; duplicates and gaps under concurrent inserts |
| **Keyset on (sort key, id) with an opaque cursor** (chosen) | Constant-time with an index; stable; tamper-checkable | No "jump to page N"; each sort option needs a matching index |
| Database server-side cursors | Very stable | Holds a connection open per user; does not fit stateless HTTP |

## Decision

1. **Request**: `GET /v1/<things>?limit=50&cursor=<opaque>&sort=<allowed key>`.
   - `limit` default **50**, maximum **100**. `limit` above 100 or below 1 returns **HTTP 422** with a
     problem+json body naming the maximum. (We reject rather than silently shrink, so clients learn.)
2. **Response**: `{ "items": [...], "next_cursor": "<opaque or null>" }`. `next_cursor` is `null` on
   the last page. No total count (counting is slow on big tables); a separate count endpoint can be
   added if the director needs it.
3. **Sort**: each endpoint publishes a small allow-list of sort keys (for example `created_at`,
   `name`, `ts`). The query always orders by `(sort_key, id)` in the same direction and uses a row
   comparison: `WHERE (sort_key, id) > (:last_sort_value, :last_id) ORDER BY sort_key, id LIMIT :limit + 1`.
   Fetching one extra row tells us whether there is a next page.
4. **Index rule**: every allowed sort has a matching index leading with `tenant_id`:
   `(tenant_id, sort_key, id)`. The data-engineer shows `EXPLAIN` output in the PR proving an index scan.
5. **Cursor format**: base64url of a small JSON object `{v: 1, sort, dir, last: [sort_value, id],
   fh: <hash of the filters>}` plus an HMAC-SHA256 signature using `CURSOR_SIGNING_KEY`.
   A cursor that is tampered with, from another endpoint, or reused with different filters returns
   **HTTP 400**. Tenancy is still enforced by the query and row-level security, so a cursor can never
   reveal another tenant's data even if forged.
6. **One shared helper** (`core/src/cp_core/pagination.py`) builds the query and cursors. Endpoints
   must use it; a test fails if any list route lacks `limit`/`cursor` parameters.

## Consequences

- Good: list latency stays flat as data grows; no duplicates or gaps while paging during ingest.
- Good: one helper means one place to test and fix.
- Cost: the web screens show "Next" / "Previous" rather than numbered pages. "Previous" is handled by
  the browser keeping the cursors it has already seen.
- Cost: adding a new sort option requires a new index (a migration).
- Named tests: `test_page_size_capped_at_100`, `test_keyset_pagination_no_duplicates_or_gaps_under_concurrent_inserts`,
  `test_ties_broken_by_id`, `test_tampered_cursor_rejected`, `test_every_list_route_is_paginated`.
